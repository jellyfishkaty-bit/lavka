# Инструкции ИИ-разработчику — «Лавка забытых историй»

GitHub — **единственный общий источник состояния проекта**. Не делай предположений о завершении задач по старым ответам чатов.

## Перед началом каждого задания

1. Прочитай [актуальный handoff](docs/handoffs/HANDOFF_LATEST.md), [протокол работы](docs/AI_WORKFLOW.md) и **связанную GitHub Issue целиком, включая комментарии**. Если открыт PR — прочитай обсуждение и review threads.
2. Проверь фактический HEAD веток, состояние PR и наличие уже выполненных изменений. Не перезаписывай существующие файлы без необходимости.
3. Уточни требования в Issue, если обнаружено противоречие. При старте существенной работы оставь короткий комментарий о фактическом состоянии и следующем шаге.
4. Работай в отдельной ветке. Для художественных экспериментов базовая ветка: art/pixel-workshop-v2; для других работ — ветка, указанная в Issue. Не изменяй main без отдельного разрешения.

## Во время работы

- Создавай маленькие проверяемые коммиты. Перед повтором операции проверяй GitHub: файл может уже существовать.
- Не загружай большие партии бинарных ассетов Base64. Проверяй контрольные суммы и ссылки на реальные файлы.
- Не придумывай прохождение тестов: фиксируй фактические команды и результаты, отделяя исторические отчёты от текущих запусков.
- Не изменяй SQLite, applicationId, подписи APK, секреты или утверждённую графику без отдельного разрешения Кати.
- При появлении замечания ревьюера в Issue/PR **прочитай и обработай его до следующей итерации**. Если не согласен — объясни фактами; не подтверждай замечания без анализа.
- Комментарий в GitHub **не запускает другую сессию Work автоматически**. Эти правила применяются, когда Work запущен и читает репозиторий.

## Перед сдачей

1. Повторно перечитай Issue и последние комментарии.
2. Сверь с критериями приёмки. Перечисли реально добавленные файлы, коммиты и выполненные проверки.
3. Открой PR. Используй «Closes #N» только при доказанном завершении задачи; при частичном результате — «Refs #N» и список оставшихся шагов.
4. Оставь PR открытым для ревью Макса, исправляй обоснованные замечания новыми коммитами и отвечай в обсуждении.
5. **Не объединяй PR и не закрывай художественные задачи без решения Кати.** Актуализируй handoff при существенных изменениях состояния.

## Роли и приоритеты

- **Катя** — владелец продукта; финальная художественная приёмка и разрешение на критичные изменения.
- **Макс** — формирует GitHub Issues, проверяет результаты как независимый технический/художественный ревьюер. Отдельная ежечасная автоматизация следит за изменениями и обращается к Кате при существенных событиях.
- **Work (Terra/Sol)** — выполняет задачу, публикует проверяемые изменения, реагирует на замечания через Issue и PR.
